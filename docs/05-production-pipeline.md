# 05. 제작 파이프라인

한 편이 아이디어에서 발행까지 가는 경로. **각 게이트를 통과하지 못하면 다음 단계로 못 갑니다.**

```
① 선정 → ② 조사 → ③ 대본 → ④ [게이트1: validate] → ⑤ [게이트2: 원문대조]
   → ⑥ [게이트3: 반대심문] → ⑦ 녹음 → ⑧ 편집 → ⑨ [게이트4: 최종검수] → ⑩ 발행
                                  ↑
                        ⑧.5 render.py 자막 영상 초안
```

## ① 선정
`python3 tools/claimctl.py calendar --weeks 4` 로 다음 4주 슬롯 확인.
우선순위 → 난이도 순으로 자동 배정됩니다. **초반에는 난이도 1~2만 하세요** —
어려운 편을 초반에 배치하면 완주율이 낮게 시작하고 채널 전체 노출이 눌립니다.

## ② 조사 (편당 2~4시간)
- `claims.yaml`의 `evidence` 항목을 출발점으로 **1차 출처를 직접 열람**
- 새 출처는 `content/sources.md`에 ID를 부여해 등재
- **초록만 읽고 쓰지 않습니다.** 최소한 결론과 방법 절은 읽으세요
- 상대 진영이 이 주제에 어떻게 반박하는지 미리 조사 → `예상 재반박`에 기록

## ③ 대본
`content/scripts/_TEMPLATE.md` 복사 → `EP0XX-slug.md`
- 모든 사실 주장에 `[S-XXX]` 마커
- `예상 재반박` 섹션을 **반드시** 작성 (영상에는 안 들어가지만 댓글 대응의 전부)
- 고정 댓글 블록까지 대본 안에서 완성

## ④ 게이트 1 — 기계 검수
```bash
python3 tools/claimctl.py validate
```
검사 항목: front matter 완결성, claim_id·출처 ID 실재 여부, 본문 마커와 선언 일치,
길이(70초 초과 시 오류), `confidence: active`의 단정 어조, 자책골 표현, 레드라인 표현.

**오류가 하나라도 있으면 녹음하지 않습니다.** 녹음 후 발견하면 재녹음 비용이 발생합니다.

## ⑤ 게이트 2 — 원문 대조 (기계 + 사람)
```bash
python3 tools/attest.py init EP0XX && python3 tools/attest.py check
```
→ [편집 정책](03-editorial-policy.md) §2 2단계
- 인용문을 원문에서 확인. 2차 인용 금지
- 숫자의 단위·오차범위 확인
- 논문 결론이 우리 서술 방향과 실제로 일치하는지

## ⑥ 게이트 3 — 반대 심문 (사람)
대본을 창조론자 입장에서 소리 내어 읽고, `예상 재반박`의 각 항목에 답이 준비됐는지 확인.
**허수아비를 만들지 않았는지**가 핵심 점검 항목입니다.

## ⑦ 녹음
- 조용한 공간, 동일 마이크·동일 거리 유지 (회차 간 음색 일관성)
- TTS 사용 시 **보이스를 절대 바꾸지 마세요.** 일관성이 신뢰도입니다
- 숫자와 학명은 **의도적으로 느리게**. 여기서 빠르면 못 알아듣습니다
- 한 문장씩 끊어 녹음하고 최선 테이크를 고르는 편이 통으로 가는 것보다 빠릅니다

## ⑧ 편집
- 컷: 3~5초마다 화면 전환 (정보 콘텐츠는 전환이 리듬을 만듦)
- **출처 자막은 증거 컷마다 하단 고정.** 없는 컷은 게이트 4에서 반려
- 색 규칙 준수: 창조론 주장 = `--claim`, 검증된 사실 = `--evidence` → [브랜드](02-brand.md) §3
- 번인 자막 56px 이상, 안전영역 준수
- 음량 -14 LUFS

## ⑧.5 제작 패키지 빌드
```bash
python3 tools/produce.py EP0XX
```
`build/EP0XX/` 에 낭독 원고·SRT 자막·샷 리스트·메타데이터·고정 댓글·체크리스트가 생성됩니다.
**⑦ 녹음 전에 빌드하세요** — `narration.txt` 가 녹음 원고이고,
`shotlist.md` 가 편집 작업 문서입니다. → [12 파이프라인](12-pipeline.md) §B

## ⑦ 음성 합성 (TTS)
```bash
python3 tools/tts.py EP0XX        # build/EP0XX/EP0XX.mp3
python3 tools/tts.py --voices     # 한국어 음성 목록
```
음성과 속도는 `tools/tts.py` 상단에 고정돼 있습니다. **회차마다 바꾸지 마세요.**
대본 front matter 의 `lang` 으로 언어별 고정 음성이 자동 선택됩니다
(`ko-KR` → InJoon, `zh-CN` → Yunyang).
합성 후 실제 길이가 출력되므로 60초 초과 여부를 여기서 확인합니다.

**`RATE` 를 바꾸면 `claimctl.py` 의 `SYLLABLES_PER_MIN` 도 같이 바꿔야 합니다.**
안 바꾸면 길이 추정이 조용히 어긋나서, 목표보다 길다고 착각하고 멀쩡한 문장을 잘라냅니다.
실측 방법은 mp3 길이 대비 SRT 대사의 음절 수입니다 (+15% → 275, +30% → 302).

**큐마다 따로 합성해 이어붙이고, SRT 를 실측 타이밍으로 다시 씁니다.**
한 덩어리로 합성하면 자막(음절 추정)과 음성이 어긋납니다 —
EP001 에서 4.7초(9%) 차이가 났고, 큐 단위로 바꾸니 0.06초가 됐습니다.
그러므로 **TTS 를 반드시 렌더보다 먼저** 돌리세요. 순서가 바뀌면 옛 타이밍이 쓰입니다.

## ⑧.5 자료 화면 배정
`produce.py` 가 `assets/EP0XX/shots.yaml` 뼈대를 만듭니다.
`file:` 에 이미지 경로를 넣으면 렌더 시 배경으로 깔립니다.
→ [assets/README.md](../assets/README.md)

**타이밍은 shots.yaml 이 아니라 현재 SRT 에서 `cue` 번호로 찾습니다.**
yaml 의 `at`/`until` 은 참고용입니다 — TTS 가 SRT 를 실측으로 다시 쓰면 어긋납니다.

**각 행의 `line:` 은 그 컷이 어느 자막에 붙었는지 적어 둔 것입니다.** 지우지 마세요.
대본을 고쳐 큐가 다시 쪼개지면 번호는 멀쩡한데 가리키는 자막만 바뀝니다.
CN01 에서 Nature 도식이 교육부 대사 위에 깔렸는데, 번호만 보면 정상이라
영상을 눈으로 볼 때까지 아무도 몰랐습니다. 지금은 렌더가 이걸 경고로 잡습니다.

**같은 파일을 연달아 배정하면 한 컷으로 합쳐집니다.** 한 도식을 여러 줄에 걸쳐
보여줄 때 큐마다 끊으면 경계에서 켄번스가 되감겨 화면이 튑니다.

빈 구간은 단색 배경입니다. 한두 박자 비우는 건 의도적으로 쓸 수 있지만
(다음 컷을 때리기 전 숨), **대부분이 비어 있으면 부실해 보입니다.**
큐 15개에 컷 3개였던 EP001 은 "자료 화면이 비어 있다"는 지적을 받았습니다.

## ⑧.6 자막 영상 초안 렌더
```bash
python3 tools/render.py EP0XX                    # TTS 음성이 있으면 자동으로 얹음
python3 tools/render.py EP0XX --audio other.wav  # 다른 녹음을 대신 얹기
```
`build/EP0XX/EP0XX-draft.mp4` 생성. **완성본이 아니라 초안입니다** —
자료 화면(화석 사진·그래프)은 편집자가 얹어야 합니다.

이 도구가 보장하는 것은 **브랜드 규격**입니다:
1080×1920 / H.264 High / yuv420p / 30fps / AAC 48kHz —
[04 플랫폼](04-platform-playbook.md) §2 의 유튜브 공식 권장값과 일치.
자막 62px·줄바꿈·안전영역(상 12% 하 20%)·출처 하단바·MYTH 컷 `--claim` 색 자동 적용.
자료 화면이 배정된 구간에는 어둠막이 깔려 자막 가독성을 확보합니다.

**화질 요소** — 정지 화면은 쇼츠에서 이탈의 주원인입니다:
- 자료 화면에 **켄번스**(느린 확대) 자동 적용. `shots.yaml`에 `kenburns: false`로 끌 수 있음
- 대본의 `**강조**`가 자막에서 `--accent` 금색으로 표시됩니다
- 자막은 0.18초 **페이드인**. 툭 나타나면 싸구려로 보입니다
- 음성은 **-14 LUFS / -1 dBTP 로 정규화**하고 스테레오 48kHz 로 내보냅니다.
  플랫폼은 초과분만 낮추고 **미달분은 올려주지 않습니다** — 조용하면 조용한 채로 나갑니다.
  정규화 전 EP001 은 -19.8 LUFS 였습니다.
  **정규화는 2패스 + 컴프레서입니다.**
  1패스만 쓰면 지정값과 결과가 어긋납니다 — CN01 은 -14 를 걸었는데 -17.3 이었습니다.
  2패스로 고쳐도 CN01 은 -16.4 에서 멈췄는데, 이건 loudnorm 문제가 아니라
  **크레스트 팩터** 문제입니다: 원본이 -26.08 LUFS 에 피크 -2.41 dBTP,
  즉 피크가 본체보다 23.7dB 높아서 진성 피크 상한(-1 dBTP)에 먼저 걸립니다.
  **볼륨을 올려도 피크가 같이 올라가므로 소용없습니다** — 압축이 필요합니다.
  임계값은 신호 본체보다 **아래**에 둬야 걸립니다(-20dB 로는 거의 동작하지 않았고,
  -30dB 에서 동작). EP001 은 원본이 -19.83 이라 올릴 폭이 작아 2패스만으로 -14.2 에 붙었습니다.

  **렌더가 끝나면 실제 값을 재서 출력하고, 목표보다 2dB 이상 낮으면 경고합니다.**
  직접 재려면: `ffmpeg -i out.mp4 -af ebur128 -f null -`
- 글자 위치는 폰트 메트릭(advance width)으로 계산합니다. 추정값을 쓰면 강조 구간에서 간격이 벌어집니다

**인코딩**은 CRF 18 + 상한 8Mbps 입니다. 예전엔 비트레이트를 8Mbps 로 고정했는데,
이 채널 화면은 대부분 단색 도식이라 그게 통째로 낭비됐습니다 —
41초짜리가 37MB 였고, CRF 로 바꾸니 눈에 보이는 차이 없이 3MB 아래로 떨어졌습니다.
카메라 영상을 쓰게 되면 이 값을 다시 보세요.

> **렌더 시간**: 켄번스는 1080×1920 프레임을 매 장 재계산하므로 비쌉니다.
> 자료 화면을 큐마다 채운 편은 **편당 수 분**이 걸립니다.
> 급할 때는 `shots.yaml` 에 `kenburns: false` 로 끄세요.

## ⑨ 게이트 4 — 최종 검수
```bash
python3 tools/claimctl.py meta EP0XX   # 체크리스트 출력
```
또는 `build/EP0XX/checklist.md` 사용 (미검증 출처 경고 포함)
체크리스트 전 항목 확인. 특히:
- 음소거로 한 번 재생해 보세요. **소리 없이 이해되면 통과.**
- 아무 프레임이나 캡처해서, 맥락 없이 돌아다녀도 오해 없을지 확인

## ⑩ 발행
- 두 플랫폼 동시, 원본 파일에서 각각 내보내기 (워터마크 금지)
- **발행 즉시 고정 댓글에 출처 전문 게시** — 미루면 잊습니다
- `claims.yaml`의 `status: published`, `episode: EP0XX` 갱신 후 커밋
- 대본 front matter `status: published` 갱신

## 사후 (48시간)
- 댓글에서 반복되는 반론 수집 → `claims.yaml`에 새 주장으로 추가 (E 기둥 소재)
- 사실관계 오류 지적이 있으면 **24시간 내 고정 댓글 정정** → [편집 정책](03-editorial-policy.md) §5

## 소요 시간 (실측 전 추정치)

| 단계 | 시간 |
|---|---|
| 조사 | 2~4h |
| 대본 + 게이트 1~3 | 2~3h |
| 녹음 | 0.5~1h |
| 편집 | 2~4h |
| 발행·사후 | 0.5h |
| **합계** | **7~12.5h / 편** |

현실적으로 잡으려면 ①②를 주말에 몰아서 3편치 배치 처리하고,
④~⑩을 평일에 나누는 구조가 낫습니다. → [런칭 계획](07-launch-90days.md)
