# 13. 외부 도구 검토

> "좋은 퀄리티의 스크립트를 뽑아줄 외부 프로젝트가 있는가"에 대한 조사 결과.
> 조사 시점 2026-09. 별 수와 유지보수 상태는 변하므로 도입 전 재확인하세요.

## 결론

**대본 생성을 맡길 만한 프로젝트는 없습니다. 도입하면 안 됩니다.**
다만 **제작 공정의 다른 구간**에는 쓸 만한 것이 있고, 빌려올 만한 **설계 아이디어**가 하나 있습니다.

| 구간 | 외부 도구 | 판정 |
|---|---|---|
| 대본 생성 | MoneyPrinterTurbo, ShortGPT 계열 | ❌ **도입 금지** |
| 영상 클립 추출 | Opus Clip 대체재 계열 | ❌ 해당 없음 (자를 원본이 없음) |
| 자막 타이밍 | WhisperX | ✅ **도입 권장** (녹음 이후 단계) |
| 음성 합성 | MeloTTS | ✅ 검토 가치 있음 |
| 출처 검증 | grounded generation 패턴 | 💡 **아이디어만 차용** |

---

## 1. 대본 생성기 — 도입 금지

### 조사한 것

`MoneyPrinterTurbo`(주제 한 줄 → 대본·음성·스톡영상·자막·BGM 전자동),
`ShortGPT`, `shortrocity` 등. 모두 같은 구조입니다:
**주제를 받아 LLM이 대본을 쓰고, 스톡 영상을 붙이고, TTS로 읽고, 자막을 얹어 내보냅니다.**

### 왜 안 되는가

이 도구들은 **분량 최적화 도구**입니다. 설계 목표가 "하루에 몇 편 뽑느냐"이고,
출처 개념 자체가 없습니다. LLM이 그럴듯한 문장을 생성하면 그대로 영상이 됩니다.

우리 리포가 하는 일은 정확히 그 반대입니다:

| 이 도구들 | 이 채널 |
|---|---|
| LLM이 사실을 생성 | 1차 출처에서 사실을 **확인** |
| 출처 개념 없음 | 출처 없는 대본은 CI에서 **차단** |
| 빠르고 많이 | 느리고 정확하게 |
| 틀려도 다음 편 | 틀리면 **정정 편 발행** |

우리가 겪은 일이 이걸 그대로 보여줍니다 — 제 기억으로 적은 DOI 하나가 **존재하지 않는 논문**이었고
(`S-NISHIKIMI-1994`), Crossref 검증이 그걸 잡았습니다. 생성형 도구는 그 검증 단계가 아예 없습니다.
**그럴듯한 서지사항을 지어내는 것이 바로 이 채널이 가장 크게 잃는 실수**입니다.
→ [03 편집 정책](03-editorial-policy.md) §2, [08 지표](08-metrics.md) §6

> **도입하면 `claimctl validate`와 `refcheck`가 존재할 이유가 사라집니다.**
> 이 리포의 가치는 도구가 아니라 도구가 강제하는 규율입니다.

### 부분적으로 쓸 만한 것

이 프로젝트들의 **FFmpeg 조립 코드와 자막 번인 설정**은 참고할 만합니다.
대본은 우리가 쓰고, 영상 조립 레시피만 참고하는 방식이면 문제없습니다.

## 2. 영상 클립 추출기 — 해당 없음

`Opus Clip` 대체재 계열(긴 영상에서 바이럴 구간을 찾아 9:16으로 잘라냄)이
검색 결과의 대부분을 차지하는데, **우리에게는 자를 원본 영상이 없습니다.**
장편 강연을 하게 되면 그때 다시 볼 것.

---

## 3. WhisperX — 도입 권장

**무엇**: 음성을 단어 단위 타임스탬프로 정렬(forced alignment).
BSD-2-Clause, 약 24k 별, 활발히 유지보수됨.

**왜 우리에게 맞는가**: 지금 `produce.py`의 SRT 타이밍은
**한글 음절 수 기반 추정치**(분당 355음절)입니다. 실제 녹음과 반드시 어긋납니다.
녹음 파일을 WhisperX에 넣으면 **실측 타이밍**이 나오고, 자막이 정확히 붙습니다.

**도입 시점**: 녹음이 시작된 뒤(Phase 1). 지금은 쓸 데가 없습니다.

**확인된 제약**: 한국어가 기본 정렬 모델 목록(`en, fr, de, es, it`)에 **없습니다.**
HuggingFace의 한국어 wav2vec2 모델을 지정해야 하고, **정렬 품질은 직접 시험해야 합니다.**
도입 전 EP001 녹음 하나로 검증할 것.

**연결 방법**: `produce.py`에 `--align <audio>` 옵션을 추가해
추정 SRT 대신 실측 SRT를 쓰게 하면 됩니다. 기존 구조를 바꿀 필요 없습니다.

---

## 4. MeloTTS — 검토 가치 있음

**무엇**: 다국어 TTS. MIT 라이선스, 약 7.6k 별, **한국어 지원 확인됨**, CPU 실시간 추론 가능.

**왜**: [05 파이프라인](05-production-pipeline.md) ⑦은 "TTS 사용 시 보이스를 절대 바꾸지 말 것"을
요구합니다. 자체 호스팅 모델은 이 일관성을 보장합니다 —
상용 API는 모델이 업데이트되면 목소리가 바뀔 수 있습니다.

**주의**: 과학 용어와 학명("틱타알릭", "등시선", "내인성 레트로바이러스")의 발음이 관건입니다.
**도입 전 반드시 이 단어들로 시험하세요.** 발음이 깨지면 그 자체로 신뢰도 손실입니다.

> **검증 실패 사례**: 조사 중 여러 곳이 `Kokoro-82M`(Apache-2.0)의 한국어 지원을 언급했으나,
> **모델 카드에서 확인되지 않았습니다.** 2차 정보를 그대로 믿지 말고 공식 문서를 확인하세요.
> 우리가 창조과학을 비판하는 이유와 같은 이유로, 우리도 2차 인용을 쓰지 않습니다.

## 5. 빌려올 아이디어 — 청구 단위 검증

이게 이번 조사의 실제 수확입니다.

RAG 평가 쪽에는 **grounded generation / faithfulness**라는 개념이 정착해 있습니다:
생성된 텍스트를 **문장 단위 주장으로 쪼갠 뒤, 각 주장이 인용된 출처에서 실제로 도출되는지**
검사하는 방식입니다. `RAGAS`, `DeepEval` 등이 이 지표를 구현하고 있습니다.

**우리 도구의 공백이 정확히 여기입니다.**

| 현재 `claimctl validate` | 못 하는 것 |
|---|---|
| 출처 마커가 **있는지** 검사 | 그 문장이 **그 출처로 뒷받침되는지**는 검사 못 함 |
| 마커와 선언의 일치 검사 | 논문 결론과 우리 서술 방향의 일치는 검사 못 함 |

지금은 이걸 사람이 합니다 — [편집 정책](03-editorial-policy.md) §2 2단계(원문 대조).
**그 단계를 없애자는 게 아닙니다.** 다만 기계가 **1차 거름망** 역할은 할 수 있습니다:

- 대본의 각 사실 문장을 추출
- 인용된 출처의 초록/본문과 대조
- 뒷받침이 약한 문장을 **경고로 표시** → 사람이 집중 검토

**단, 이건 도구 도입이 아니라 우리가 만들 기능입니다.**
외부 RAG 프레임워크를 통째로 들이면 의존성이 무거워지고([12 파이프라인](12-pipeline.md) §D
"PyYAML 하나와 curl 뿐"이라는 원칙 위반), 1인 운영에서 유지보수가 안 됩니다.

> **주의**: 이 기능이 생겨도 §2 2단계를 생략하면 안 됩니다.
> 기계 대조는 초록 수준이고, 논문의 **결론 방향**은 사람이 읽어야 압니다.

## 6. 실행 순서

```
지금        아무것도 도입하지 않음. 대본은 계속 사람이 씀
Phase 1     EP001 녹음 후 WhisperX 한국어 정렬 시험 → 되면 produce.py 에 연결
Phase 1     MeloTTS 를 과학 용어로 시험 → 발음 통과하면 채택
Phase 2+    청구 단위 검증을 자체 구현 (외부 프레임워크 도입 아님)
영구        대본 생성기는 도입하지 않음
```

## 7. 한 줄 요약

> 대본 품질을 높여주는 외부 프로젝트는 없습니다.
> 있는 것들은 **분량을 높여주는 도구**이고, 그건 우리가 피하려는 실패 방식입니다.
> 외부에서 가져올 것은 **녹음 이후 공정**(정렬·합성)과 **검증 설계 아이디어**뿐입니다.
